Technical Requirements Document (TRD)

AI-Powered Prep Manager

Version: 1.0 | Status: Draft | Companion to: PRD v1.0

1. System Overview

A pipeline that takes prep photos + category metadata, extracts visual evidence (objects, text, spatial layout), evaluates that evidence against a versioned rule engine (not the LLM's judgment alone), and returns structured per-check verdicts plus an aggregated status.

[Images + Metadata]
        │
        ▼
 ┌───────────────┐
 │ Preprocessing │  (quality gate, orientation, crop/zoom regions)
 └───────┬───────┘
         ▼
 ┌────────────────────┐
 │ Perception Layer    │  VLM detection + OCR + spatial geometry
 └───────┬─────────────┘
         ▼
 ┌────────────────────┐
 │ Rule Engine          │  category → applicable checks → evaluate evidence
 └───────┬─────────────┘
         ▼
 ┌────────────────────┐
 │ Aggregator + Report  │  per-check verdicts → overall PREP STATUS
 └───────┬─────────────┘
         ▼
 [Structured JSON + human-readable report] → logging/audit store

2. Components

2.1 Preprocessing

  • Image quality gate: blur, exposure, resolution thresholds. Images below threshold are tagged low_quality, which downstream forces UNCERTAIN on any check relying on that image.
  • Category resolution: map SKU/ASIN or manual category input → applicable rule subset.
  • Region proposal: locate label(s), barcode(s), seams/edges as candidate crops for downstream perception (reduces false negatives on small text).

2.2 Perception Layer

Multiple specialized extraction passes, each producing structured evidence (not a verdict):

Module Function Output
Object/segment detector Locate polybag boundary, seal line, label(s), barcode region(s) bounding boxes + confidence
OCR engine Extract text from suffocation-warning label, expiry date field, handling-mark text/icons text + confidence + bbox
Barcode/label reader Decode FNSKU and manufacturer barcode if legible decoded value + type + confidence
Spatial/geometry module Determine surface flatness/curvature under label region; detect seam crossing surface classification + confidence
Seal/closure classifier Classify polybag opening as sealed/unsealed/taped/heat-sealed classification + confidence

All modules emit evidence with confidence scores, never a pass/fail — verdict logic lives entirely in the rule engine.

2.3 Rule Engine

  • Consumes a versioned, structured rule set (JSON/YAML) — the authoritative source referenced in the challenge — keyed by category and check type.
  • Each rule defines: check ID, applicability condition (category, product type), required evidence type(s), pass condition, fail condition, and the confidence threshold below which the check must resolve to UNCERTAIN.
  • Example rule schema:
{
  "check_id": "fnsku_placement",
  "applies_when": {"category": "*"},
  "required_evidence": ["fnsku_bbox", "surface_classification"],
  "pass_if": "surface_classification == 'flat' AND fnsku_bbox.confidence >= 0.8",
  "fail_if": "surface_classification IN ['seam','curved_edge','opening']",
  "uncertain_if": "surface_classification.confidence < 0.6 OR fnsku_bbox is null"
}
  • The rule engine is deterministic given evidence — this is what prevents the model from "inventing" compliance rules; the LLM/VLM never decides pass/fail directly, it only supplies evidence that the engine evaluates.
  • Rule set is versioned; every verdict is stamped with the rule-set version used, for auditability.

2.4 Aggregator + Reporting

  • Applies the overall-status rule (§6 of PRD): any FAIL → overall FAIL; else any UNCERTAIN → overall UNCERTAIN; else PASS.
  • Produces both a machine-readable JSON payload and the human-readable report format shown in the PRD/challenge example.
  • Attaches evidence (cropped image regions, OCR text, confidence) to each check for reviewer traceability.

4. Reference Rule Set Management

  • Stored as versioned config, not embedded in prompts or model weights.
  • Update workflow: new/changed requirement → rule authored/reviewed by compliance owner → versioned release → rule engine hot-reloads without redeploying the perception layer.
  • Category-to-checks mapping is explicit and inspectable (no implicit LLM inference of "which rules apply").

5. Handling Non-Verifiable Requirements

  • Each rule declares whether it is visually_verifiable: true/false.
  • Non-visual requirements (e.g., material thickness) are marked visually_verifiable: false at the rule-set level and are always reported as UNCERTAIN / NOT VERIFIABLE FROM IMAGE, and excluded from the FAIL-triggering logic — they should never contribute a false FAIL or false PASS.
  • Any check where required evidence modules return null or below-confidence-threshold results in UNCERTAIN, with the specific missing evidence named in the reason (e.g., "expiry date region not visible in any supplied image").

6. Model/Tech Approach

  • Perception: vision-language model(s) for detection/description + dedicated OCR engine (for robustness on small/low-contrast text) + barcode decoding library + a lightweight geometry/segmentation model for surface/seam classification.
  • Reasoning/orchestration: an agent loop that (1) calls perception modules as tools, (2) assembles evidence, (3) invokes the deterministic rule engine, (4) formats output. The LLM does not author verdicts from general knowledge — it is constrained to calling tools and evidence assembly; final pass/fail computation is rule-engine code, not free-form generation.
  • Confidence thresholds: tunable per check; conservative defaults (favor UNCERTAIN over PASS).

8. Non-Functional / Engineering Requirements

  • Determinism: identical inputs + rule-set version → identical verdicts (perception confidence variance aside).
  • Auditability: every review stores rule_id + evidence + rule_set_version; immutable log.
  • Latency target: p95 < 8s per unit for up to 4 images.
  • Extensibility: adding a check = adding a rule + (if needed) a new evidence extractor; no core pipeline rewrite.
  • Observability: per-check verdict distribution, UNCERTAIN rate, and confidence histograms tracked for drift/calibration monitoring.
  • Human-in-the-loop: override endpoint writes corrections back into a calibration dataset for periodic threshold/model tuning (not automatic retraining in v1).

9. Evaluation Plan

  • Curated test set covering all 10 scenarios in PRD §11, plus category-specific variants.
  • Metrics: per-check precision/recall, false-PASS rate (target ≈ 0), UNCERTAIN calibration (UNCERTAIN should correlate with genuinely low-evidence cases, verified by human audit).
  • Regression suite re-run on every rule-set version bump and every perception-model update.

10. Security & Data Handling

  • Images may contain product/brand identifiers — access-controlled storage, retention policy aligned with compliance audit needs.
  • Rule set treated as sensitive configuration (change-controlled, versioned, reviewed).

11. Open Technical Questions

  • Source/format of the authoritative rule set at launch (manual JSON authoring vs. ingestion from an existing policy document)?
  • Minimum required image angles/count per unit — enforced at capture time or handled as UNCERTAIN downstream?
  • Where does human review sit in the flow — pre-ship gate on FAIL/UNCERTAIN, or post-hoc sampling only?
